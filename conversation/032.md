## 12:10

I want to add a mechanism that will allow someone else to take over the RBR project if I die or become otherwise unable to continue. The basic aim is to provide reassurance to customers that they will not be left with an unsupported product.

It starts with a new page on the website: handover/. In the config file above the site root is a new field, "handover", containing a passphrase. This will have been given in a sealed envelope to each of the customers (heating installers), to be used in the event of my being unavailable. In such an event, they or their new technical advisor will visit the handover page, which will present a form asking for the passphrase and the URL of a new and already prepared website.

When this form is submitted, the identity of the requester will be stored and I will be sent an email to notify me. In addition, the PWA will display a prominent flashing message at the top of the screen, but only for me. This may mean that when the PWA contacts the website it includes its system MAC as part of the request.

To cope with false triggering, nothing else will happen for 14 days, during which time I can cancel the handover request and take whatever action is needed, knowing who the requester was. After that period, the system controller will be notified on its next update query that a change of URL has occurred, and it will switch to that. This will also include a re-identification of the public MQTT broker if this has changed.

If the new URL does not exist or does not respond appropriately, the handover will fail. Obviously, all this requires action by the customer or myself to prepare for this procedure to run; this will be covered by a separate project.

If the above is complete enough, please start. Otherwise we can continue a discussion.

**Assistant**

The handover mechanism is implemented end to end.

**What is now in place**

- `/handover/` is a no-index page with the passphrase and new-site fields, a warning that nothing changes immediately, and a cancellation-link mode. It posts to `handover.php`.
- `handover.php` records the request with the requester's IP, forwarded-for header, user agent and timestamp; emails the owner; and starts the waiting period. The request state lives in `rbr-handover.json` above the web root, mode 0600, under a lock. The passphrase is never stored or echoed.
- The default waiting period is 14 days (`days` can change it). During it the PWA shows the owner a flashing banner with the days left and a Cancel button. Cancellation also works from an HMAC-signed link in the notification email, so it does not depend on the app having a token.
- On the first status query after the period, the new site is checked again. If it passes, the request becomes `active`; if not, it becomes `failed`, the owner is emailed, and nothing switches.
- Every controller asks its current site for handover state on each hourly updater run. An active handover writes the new address to `.site_url` and reconciles mosquitto's bridge `address`, `remote_username` and `remote_password` from the new site's `credentials.php`. The broker port comes from `mqtt_port` (default 8883), separate from the browser's websocket `port`.
- A controller without a token can still learn that an active handover exists and its URL; it cannot see a pending request or fetch the new broker account. A controller with a token gets the full status.
- The readiness contract is: HTTPS (unless testing), public address, `/heat/version` returns a numeric RBR release stamp, `/credentials.php` answers 401 without a token, and redirects are not followed. The request is refused at submission if it fails, and the updater checks the same stamp again before switching.

**Assumptions I made**

- The config field is `handover`. It can be the passphrase alone, or an object with `passphrase`, `owner_mac`, `notify` and `days`. `owner_mac` is what makes the PWA alert owner-only and enables cancellation from the app; without it, the email link still cancels. I supported this richer form because the plain passphrase alone gives the server no way to know which system is yours.
- `notify` is the notification address; if it is omitted, the address registered for `owner_mac` in `rbr-users.json` is used, and `mail_from` is the last fallback.
- The form's address is the new site root. The updater appends `/heat/rbr-controller.tar.gz` and `/credentials.php`.
- A controller can only act after it has taken a release containing the new updater code. That release has to travel through the old update path first; this is documented in `doc/HANDOVER.md`.
- The 14-day channel is a technical cancellation window, not the 30-day continuity trigger. It does not transfer the domain, hosting, broker or repository.
